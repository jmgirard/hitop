# M052: A stepped flow for the browser module builder

**Status:** done (2026-08-24, PR #58 https://github.com/jmgirard/hitop/pull/58)

**Goal:** The HiTOP-SR Module Builder presents its work as a progression — choose scales, set options, download — instead of one long column, with every file it builds unchanged.

**Outcome:** In `jmgirard/hitop-builder` (PR #3, commit `871fe1c`): `index.html`'s controls regrouped into three `section.step` blocks shown one at a time. A `nav#stepbar` above them carries three buttons, each `data-goto` an index, the current one marked `aria-current="step"`; the same `data-goto` attribute drives the Back/Continue pair at each step's foot and a *Change the selection* link in the recap, so one handler wires every move. `showStep()` toggles the `hidden` attribute, refreshes the recap and focuses the arrived-at step's `h2` (`tabindex="-1"`, ringed by a `.step > h2:focus` rule, since programmatic focus does not match `:focus-visible`); the first paint calls it with focus suppressed. `selectionSentence()` is factored out of `refreshTally()` and writes both the tally under the scale list and the recap line at the head of steps two and three. The status line and the log stay page-level, outside the steps. Nothing gates moving on: the download step is reachable with no scale ticked, its buttons disabled with a hint saying why. `README.md`'s *What the page shows* walks the three steps in page order and the three "Under **Download**" sections now read "Under **Set options**". The R package is untouched — this repo's diff is tracking files only.

**Decisions:** None milestone-local. Two plan gates (a stepped progression over a two-column reflow or leaving the element order alone; no persistent selection summary, light/dark switch or pinned download buttons) and one implementation gate (one step on screen at a time with a jumpable step bar, a count-and-items recap on the later steps, status line and log page-level, both opening paragraphs above the steps).

**Review:** All six criteria verified fresh. 16/16 AC1 matrix cells identical across six compared fields against a same-session capture from the deployed M051 page, confirmed byte-identical to the builder repo's `origin/main` (both pages `hitop` 0.2.0, 76 scales); four Word cells differ by one raw zip byte only. Every step boundary crossed by real Tab presses; 87/19/12 focusables enumerated per step and all reached, a 3px ring on every one of 134 focus events; the live-region query returned exactly `#status` (polite) and `#log` (`off`) on each step. Six width × scheme cells × three steps: 182 controls per cell, 0 clipped, no horizontal document scroll. Four numbering × selection combinations matched their built file (11 crosswalk pairs in the one case claiming them, none in the other three). Eleven rendered control-group titles all verbatim in the README. Every detector shown able to fail on a planted defect. Gate clean: `cairn_validate` exit 0, `document()` no diff, `test()` 13897 passing, `check()` 0/0/0, `check_pkgdown()` clean; 8 CI jobs green. Three lenses run inline, not in fresh-context subagents (session configured not to spawn agents). Three findings, none a criterion failure: the README's Back-and-Continue sentence overstating what steps one and three carry (fixed on the branch, AC6 re-run clean); `refreshTally()` re-querying the selection four times per call (rejected — no observable effect); `list-style: none` on the step bar dropping list semantics in VoiceOver (rejected — the `nav` label and `aria-current` carry the position, and there was no list before this milestone). Nothing retired; the M045 browser-driving lesson extended.
