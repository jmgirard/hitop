# M089: One download per builder build — a zip bundle holding the questionnaire, the scoring file and a README

**Status:** done (2026-09-11, PR #97 https://github.com/jmgirard/hitop/pull/97 tracking; code in jmgirard/hitop-builder PR #14 https://github.com/jmgirard/hitop-builder/pull/14)

**Goal:** A visitor to the HiTOP-SR Module Builder clicks once per build and receives one file, a zip bundle carrying the questionnaire, its scoring descriptor and a README saying what to do with each.

**Outcome:** In hitop-builder, `download()` writes the questionnaire, the `.json` descriptor and a page-authored `README.txt` under `/tmp/bundle` in webR's FS, zips them with `zip::zip(mode = "cherry-pick")` through the package's own {zip}, and saves one `<stem>.zip`; the REDCap dictionary is named `<stem>-upload.zip` inside it. `bundleReadme()`/`BUNDLE_WHAT` author the README per format, the REDCap text alone saying to upload the inner zip unextracted. The two-button descriptor handover (`offerDescriptor`, `takeDescriptor`, `#saveDescriptor`, `#handover`, `#handoverLive`), `#renameNote`, `saveFile()`'s `origin` argument and `FORMATS[].mime` are gone; `#descriptorNote`, `#downloadHint` and the three `#downloadBtn` labels (`(.zip bundle)`) speak of one file. `tests/smoke.spec.js` reads the bundle through a central-directory reader (`zipEntries`, `zlib.inflateRawSync`) with assertions A4 (entry names), A5/A6 (the `.docx` entry); `tests/plants.mjs` gained plants g and h. README.md's intro, *How it works*, *What the page shows*, *The scoring file* (quoting a captured REDCap README) and the five-column naming table follow. This repo: tracking only.
