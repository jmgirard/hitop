# M075: One REDCap archive writer, using a per-call temporary directory it always cleans up, against a stated {zip} floor

**Status:** done (2026-08-31, PR #81 https://github.com/jmgirard/hitop/pull/81)

**Goal:** Both REDCap archive-writing blocks become one internal function that builds its data-dictionary CSV inside a directory created for that call and removes it whether or not the archive write succeeds, and `DESCRIPTION` states the `{zip}` version floor the `mode = "cherry-pick"` call needs.

**Outcome:** `write_redcap_zip(data_dictionary, file)` in `R/generate_redcap.R` is the only `zip::zip()` call site in `R/`; `build_redcap_zip()` and `generate_redcap_hitophsum()` both call it, and it absorbed the whole duplicated block (relative-to-absolute destination path, scratch CSV, archive write, success message), not only the two lines the plan named. It creates `tempfile("hitop-redcap-")`, registers `unlink(recursive = TRUE)` on exit *before* `dir.create()`, then writes `instrument.csv` inside it — so two exports in one session never share a scratch path, and a failed export leaves nothing behind. Both blocks previously wrote `file.path(tempdir(), "instrument.csv")` and removed it only after a successful `zip::zip()`. `DESCRIPTION` Imports reads `zip (>= 2.1.0)`, the earliest release whose `zip()` accepts `mode = "cherry-pick"` (CRAN release notes first mention `mode` under 2.1.0; the r-lib/zip source at tag `v2.1.0` defines `mode = c("mirror", "cherry-pick")`; `zip_2.1.0.tar.gz` dated 2020-08-10). Three tests at `test-generate_redcap.R:370`, `:406`, `:437` — path capture over two `generate_redcap_hitopsr()` calls and one `generate_redcap_hitophsum()`, plus two injected failure mechanisms (a classed error from a mocked `zip::zip()`; a destination inside a directory that does not exist) run through both generators. The six committed `inst/extdata/*_redcap.zip` artifacts and their `pkgdown/assets/downloads/` copies were deliberately not rebuilt: no archived byte changes, so a rebuild would churn the checksum manifest and record a revision that is not one.

**Decisions:** D-050 — the `zip (>= 2.1.0)` floor (extending D-035, which adopted {zip} with no version stated), declared in `DESCRIPTION` alone because R enforces an `Imports` floor at namespace load; it also records the deferred artifact rebuild.

**Review:** All five criteria met with fresh evidence; AC1 and AC2's red claims re-run against a scratch clone of `main` carrying only this branch's test file. `cairn_validate` exit 0, `devtools::check()` 0/0/0, `check_pkgdown()` clean, CI green on all eight jobs. Full three-lens fan-out (user-facing tier): blame-history and prior-PR-comments returned no findings — no archived `## Review` section touches these files and the repo has no inline PR comments at all. [O] diff-bug returned eight, none demonstrating an acceptance criterion failing. Three carried to one candidate row: cleanup after a *successful* export has no assertion of its own (a mutant is caught only because an earlier test's leak is still in `tempdir()` when the failure tests run their by-name checks); `grepl("^/|^[A-Za-z]:", file)` treats `~/out.zip` as relative and prepends `getwd()`, Windows UNC paths likewise; and the `zip` floor is sourced, never exercised, while zip 2.3.0's notes mention better handling of absolute paths containing `:`. Three rejected: an unchecked `dir.create()` return (a fresh `tempfile()` name, and the next line still errors with cleanup registered), the `setdiff(list.files(tempdir()), before)` assertions (that before/after listing is what AC2 names in so many words, and the by-name assertions sit beside them for exactly the blindness raised), and a misquote of `NEWS.md`, whose shipped text says two exports "used one file" rather than that one overwrote a file in use.
