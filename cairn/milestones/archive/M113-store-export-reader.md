# M113: The package reads a store's CSV export and an article walks the Google Sheet route end to end

**Status:** done (2026-09-24, PR #125 https://github.com/jmgirard/hitop/pull/125)

**Goal:** Make `read_form_responses()` read a file holding many participants' rows, and publish an article that walks a researcher from a study link through a Google Sheet to scored data.

**Outcome:** `read_form_response_file()` reads N response rows instead of exactly one. The whole-number, integer-range, `form_build` and `submitted` checks run down each column. A header with no response row is refused by name, unclassed under D-064. `do.call(rbind, parts)` binds files in path order and rows in file order. Two fixtures come from hitop-form `c15e149` with CR bytes removed: `inst/examples/responses-sheet-hitopbr.csv`, the Google Sheet download with participants `=1+1` and `007`, and `tests/testthat/fixtures/supabase-hitopbr.csv`, the Supabase export with `p001` and `p002`. Each is read and scored in one test through `expect_hitopbr_export()`, which recomputes per-row means from the file's text and the keying tables. The new article `vignettes/articles/online-collection.Rmd` sits under Tutorials. Its steps are deploy the script, make the link, download the sheet, read, score, then the Supabase route and "Who holds the data". That section says the vendor holds the rows, the host receives the link and no answers, codes are the researcher's to make pseudonymous, and a BAA or DPA is the institution's. It cites no law and calls no store compliant. The hitop-form sections of `modules-hitopsr.Rmd` and `pid5_scoring.Rmd` no longer say the page saves a file, sends nothing, or reads one row per file, and they point at the article. The help page and NEWS were updated. AC2 was amended at implement to two rows for the Supabase export, because the file holds two participants.
