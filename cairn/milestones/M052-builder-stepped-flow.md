## Goal

The HiTOP-SR Module Builder presents its work as a progression — choose scales, set options, download — instead of one long column, with every file it builds unchanged.

## Scope

Surface tier: **user-facing** — the deliverable is a public web page researchers visit. The interaction model is page behaviour, outside IP1 (D-038); what the generated documents contain is not, which is what AC1 fences.

The work lands in the sibling repo `jmgirard/hitop-builder` (single file `index.html`), on a branch and PR there; this repo carries only the tracking record. It builds on M051's visual system rather than restating it.

**In:** the page's element order and the markup and script that drive a stepped progression; whatever indication of progress and current selection the steps themselves need; the wide-screen and narrow-screen layouts of each step; `README.md` where the reorganization makes it wrong.

**Out:** a separate persistent selection summary, a light/dark switch, and pinned download buttons — each declined at the 2026-08-24 plan gate. Any new control exposing a generator argument the page does not expose today → the standing candidate rows. Any change to what the `hitop` package generates. Tests, CI or a package version pin for the builder repo → its candidate row. Any change in this repo's R package.

## Acceptance criteria

- [x] AC1: For each of the three formats, a file built from the branch page has the same content as the file the M051 page builds from the same selections and settings, across this matrix: {a named two-scale selection, every scale} × {Word: US Letter and A4, numbering 1-to-n and original, shuffle off} × {Qualtrics and REDCap: the package defaults, and one named non-default naming set}. The Qualtrics `.txt` is compared byte for byte, the REDCap archive's `instrument.csv` line for line, and the Word file has the same header text and the same printed item rows, parsed back out of it (a DOCX is not byte-reproducible). Both pages report the same `hitop` version, which each prints on load; a version that moves between captures is re-baselined.
- [x] AC2: Every step the page defines is reachable and leaveable by keyboard alone from the step before it, and each step's controls — enumerated by querying the rendered DOM for the focusable set while that step is shown — paint the focus indicator M051 established. Querying the DOM for elements carrying `aria-live` or a role with an implicit live value returns exactly the status line (polite) and the log pane (`off`), whichever step is shown.
- [x] AC3: At viewport widths of 360, 768 and 1280 CSS pixels, in both colour schemes, every step renders its own controls unclipped — each control's bounding rectangle lies within its container's — and the page's document scrolls vertically only (`documentElement.scrollWidth <= clientWidth`).
- [x] AC4: Each notice the page can show appears on the step carrying the control it qualifies, and each of the four numbering × selection combinations shows a shuffle notice whose crosswalk sentence matches what the Word file built under that same combination actually contains, verified by building the file in each of the four and reading its scoring page back.
- [x] AC5: Reaching the download controls and building each of the three formats is possible from a first load with no scale ticked, by keyboard alone, and the download controls stay unavailable while no scale is ticked.
- [x] AC6: Every control-group title the page renders, read out of the elements that carry those titles, appears verbatim in `README.md`, and the README describes the page's steps in the order the page presents them.

## Review

Reviewed 2026-08-24 on `m052-builder-stepped-flow` (this repo, PR #58) and `m052-stepped-flow` in `jmgirard/hitop-builder` (PR #3). The default branch had not moved in either repo since the branches were cut. The deployed page at `jmgirard.github.io/hitop-builder` was confirmed by SHA-256 to be byte-identical to the builder repo's `origin/main` `index.html`, so it is the M051 page AC1 names; the branch page was served locally from the branch working tree. Both pages reported `hitop` 0.2.0 and 76 scales on load.

- AC1 — verified. All 16 matrix cells were built fresh on each page in this session (32 builds): {two named scales, agoraphobia + callousness; every scale} x {Word: US Letter and A4, numbering 1-to-n and original, shuffle off} and {Qualtrics, REDCap: the package's own defaults, read off each page's prefilled boxes, and one non-default naming set}. Six fields per cell were compared (download file name, scale count, and per format the Qualtrics byte digest, the REDCap `instrument.csv` line digest plus archive entry list, and the Word file's parsed paragraph text, table-row text, header text, page size): 16/16 identical, 0 mismatches. Four Word cells differ in raw zip byte size by one byte (18392/18393, 18426/18427, 18432/18433, 70603/70604) — the DOCX non-reproducibility the criterion anticipates, which is why the parsed content and not the byte count is the key. The comparison was shown able to fail: tampering with one digest in one cell returned exactly that cell and field, twice, on different formats.
- AC2 — verified. Every step boundary was crossed by keyboard alone, the control reached by real Tab presses and then activated: step 1 to step 2 by *Continue to options*, step 2 to step 3 by *Continue to download*, step 3 to step 2 by *Back to options*, step 2 to step 1 by *Back to scales*, step 3 to step 1 by *Change the selection*, and step 1 to step 3 by the step bar. Focus rings: the focusable set was enumerated from the rendered DOM while each step was shown — 87, 19 and 12 elements — and every element was reached by real Tab presses (92, 24 and 18 focus events) with a 3px solid outline painted at every one, 0 without a ring. The two exceptions are the unchecked radios in each of the two radio groups, which a browser reaches with arrow keys rather than Tab; the driver cannot deliver an arrow key with a `code`, so both were focused directly under keyboard modality and both match `:focus-visible` and paint the same ring. The ring detector was shown able to fail: an `outline: none` planted on one scale checkbox was reported as exactly that element and nothing else. Querying for `aria-live` or a live role returned exactly `#status` (polite, `role=status`) and `#log` (`off`, no role) on each of the three steps.
- AC3 — verified. Six cells (360, 768 and 1280 CSS pixels x light and dark) x three steps: 182 controls per cell (156 + 21 + 5), 0 with a bounding rectangle outside its container's, and `documentElement.scrollWidth == clientWidth` in all six. Both detectors were shown able to fail: a control given a 3000px minimum width was reported by name with its overhang, and the overflow check went false in the same state.
- AC4 — verified. The rendered DOM carries one notice, `#shuffleNote`, on step 2 inside the *Word item order* fieldset — the group holding the shuffle checkbox it qualifies. The other notice in the source is the `noscript` block, which speaks for the whole page before any step and is not parsed into the DOM while scripting is on. All four numbering x selection combinations were driven with shuffle on and each built file read back: 1-to-n x two scales claims a crosswalk and its file carries `Item Number Crosswalk (printed number -> original HiTOP-SR number)` with 11 pairs; the other three disclaim one and carry no such heading and no arrow pairs. The detector found the crosswalk in the one case that has one, so the three zeroes are informative rather than an empty search.
- AC5 — verified. From a first load with no scale ticked, four real Tab presses reached the step bar's *Download* button; activating it showed step 3 with all three download buttons disabled and the hint saying they turn on once a scale is ticked. One Tab reached *Change the selection*, which returned to step 1; four more Tabs reached the first scale checkbox, ticking it enabled all three buttons; four Shift+Tab presses reached the step bar's *Download* button again, and Tab then reached each of the three download buttons in turn — Word, Qualtrics and REDCap each built and delivered a file. Because of a driver limitation, activation is `.click()` on the element real Tab presses focused: the driver's Enter, Space and arrow keys arrive with an empty `code`, which Chrome requires before running a control's default activation. The page registers no `keydown`, `keyup` or `keypress` handler and calls `preventDefault` nowhere, so nothing in it stands between a real key press and the native activation.
- AC6 — verified. Eleven control-group titles were read out of the rendered elements that carry them — the four `legend`s, the three step headings, the three step-bar button labels, the `#scales` group label, the filter's `aria-label`, the log heading, and the step bar's own `Steps` label — and all eleven appear verbatim in `README.md`. The README's numbered walkthrough runs *Choose scales*, *Set options*, *Download*, the order the page presents them.

**Review lenses.** The three lenses were run inline rather than in fresh-context subagents, the session being configured not to spawn agents — the same substitution recorded at M048 through M051. Three findings, ranked, none an acceptance-criterion failure and none load-bearing:

1. `README.md` says "each step also carries Back and Continue buttons at its foot", but only step 2 carries both: step 1's `.stepnav` holds *Continue to options* alone and step 3's holds *Back to options* alone. The sentence is added by this branch and overstates what the page renders.
2. `refreshTally()` calls `selected()` four times per invocation — once through `selectionSentence()` and once per download button — where the function it replaced computed the selection once and reused it. Each call walks all 76 checkboxes, and the function runs on every selection change.
3. `#stepbar ol` sets `list-style: none`, which in Safari with VoiceOver drops the list semantics, so the step bar is no longer announced as a three-item list. The `nav` landmark's `Steps` label and `aria-current="step"` still convey which step is current.

Nothing from the archived review record on these two files is reintroduced or contradicted: M045's log-pane `aria-live="off"` decision, the wiring-time `refreshShuffleNote()` call that covers a bfcache restore, M048's and M049's shuffle and numbering logic, and M050's naming controls all move through the diff unchanged and were re-verified above.

**Triage (2026-08-24 gate).** Finding 1 fixed on the branch: the sentence now says which of Back and Continue each step carries (hitop-builder `57c8c68`); AC6 was re-run against the edited README and both clauses still hold. Findings 2 and 3 rejected — the repeated `selected()` call has no effect a visitor can observe, and the step bar's position is still carried by the `nav` landmark's label and `aria-current="step"`, with no list semantics there before this milestone to regress. Merge of both PRs approved at the same gate.
