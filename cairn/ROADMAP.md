## Candidates

- The package's three item-column naming patterns disagree: `ku_hitopsr` uses `hsr001`, `sim_hitopsr` uses `hsr_1`, and `rename_hitopsr_items()` produces `HSR_1` by default. Each is internally consistent and nothing is wrong today — the help-page examples and the modules article each build names to match the frame in hand — but a reader moving between the two datasets, or following the renamer's output, must rewrite the selection idiom each time, which is the idiom M44 set out to make routine. Settling on one pattern renames a shipped dataset's columns, a GP2 change owing NEWS and a D-entry, so it is not a doc fix. Promote if a user reports a selection failure moving between the datasets, or when a data-regeneration milestone next touches the `*_hitopsr` datasets — added 2026-08-21 — lineage: M44 (review finding, rejected at triage as pre-existing)
- The AST-walk self-check that certifies `test-plot_pid5.R` reads no plot internals discriminates by the *receiver* of a `data` extraction but not by the *accessor*: `attr(p, "data")` reads it (ggplot2 4.x objects are S7, so properties are attributes), as do `p[[key]]` with a variable index, `do.call("[[", list(p, "data"))`, and `base::`-qualified accessors — all verified to leave the guard green. No such read exists in the file today, so this is guard strength rather than a live defect. The same walk treats only `for` as a loop, so `while`/`repeat` bodies escape the in-loop `info =` rule. Promote on any read of a plot's internals reaching that file past the guard, or on the guard being reused for a second test file — added 2026-08-13 — lineage: M40 (review findings scored 74 and 55, below the actioning threshold)
- `score_hitopsr()` and `score_hitopbr()` return a `_se` value beside a scale score that is `NA`, where `score_pid5()` masks it — the engine gates this on `mask_se_na`, which only `score_pid5()` passes as `TRUE` (`R/score_engine.R:126`, `R/score_pid5.R:152`), and the code comment there calls the SR/BR behavior historical rather than chosen. Reproduced 2026-08-13 on `sim_hitopbr` with one item of respondent 1 set to `NA`: `score_hitopbr(items = 1:45, missing = "complete", calc_se = TRUE)` returns `hbr_antagonism = NA` with `hbr_antagonism_se = 0.3273268`, because `calc_sem()` drops the missing item while `missing = "complete"` drops the whole score. Neither help page nor vignette mentions the difference. Surfaced by the `calc_se` help-page hotfix (PR #45), which documented the masking for the PID-5 and correctly claimed none for SR/BR. Unifying the two changes scored output, so it is a GP2 change owing NEWS and a D-entry, not a doc fix — and which behavior is right is the open question. Promote if a user reports a standard error beside a missing score, or when the next milestone touches the scoring engine — added 2026-08-13
- `calc_se` is demonstrated in no PID-5 vignette but the short-form one — the full-form and brief-form scoring vignettes have no standard-error section at all, so the only worked `calc_se` example for the 220-item and 25-item forms is the `?score_pid5` help page. The BF case differs from the other two rather than merely repeating them: its 5 domains score straight from items with no facet layer, so its standard errors are item-based where the SF's domain standard errors are not. Promote if a reader is ever unable to work out `calc_se` for the full or brief form from the short-form vignette and the help page — added 2026-08-04 — lineage: the vignette standard-error hotfix (PR #43), which corrected the description where it existed and added none where it did not
- The documented ~7-inch figure-width floor for `plot_pid5()`'s value labels rests on a single hand measurement, on one device with one font — the review measured the worst case (a three-digit value at the axis maximum on a facet profile) as needing ~0.402in against ~0.382in of padding at 7in, i.e. essentially no margin, and the binding constraint is panel width, which differs by an inch or more between `level = "domain"` and `level = "facet"`. A per-level floor, or a measurement repeated across graphics devices, would replace the single number. Promote if a clipped label is reported at or above the documented width — added 2026-08-04, annotated 2026-08-06: M40 makes the padding conditional on `labels`, which leaves this floor where it stands (it binds only with labels on) — lineage: M39 (review findings scored 60 and 58), scoped out of M40

- Confidence intervals on PID-5 profile plots — added 2026-08-01, corrected 2026-08-04, superseded 2026-08-13 by Johannes Zimmermann's norms proposal (four artifacts supplied by Jeff 2026-08-13: `hitop_package_norms_proposal.md`, `norms_de_prolific2024.R`, a 9,984-row norms CSV and its metadata CSV; not yet placed on the `references/sources/` shelf — observed 2026-08-13). The interval method is now the regression-based true score with scale correction (Schmukle, 2025, *Assessment*, 33, 817-825): estimate `50 + sqrt(rel) * (T - 50)`, bounds `± z * 10 * sqrt(1 - rel)`. This displaces the row's earlier `SEM = 10 * sqrt(1 - alpha)` framing and settles its open "measurement vs estimated-true-score" question in favour of the estimated-true-score form, whose reference-group caveat Johannes flags and handles with a fallback to the observed-score interval. The blocker is confirmed unchanged 2026-08-13: markon2024 prints no reliability coefficient anywhere this repo has ingested, so no scale of any shipped instrument can carry an interval today. Krueger et al. (2012) Table 2 (PMC3413381, figures still unverified) remains the only *known* candidate and mismatches the norms three ways — N=264 development sample vs the book's N=995 weighted norming subsample, 220-item form only, alpha rather than ordinal omega. Jeff has a further reliability source to supply (2026-08-13). Promote once a per-scale reliability traceable to the norming sample is ingested and verified — lineage: M38
