### D-018 (2026-07-30): Validity-scale names follow the scale-development papers, not Markon et al. (2024) — `INC` is not renamed to `VRIN` (annotates D-017's M25/M26 norms arc)

The PID-5 book (Markon, Fossati, Somma & Krueger, 2024) calls Keeley's full-form
inconsistency scale "VRIN" where this package calls it `INC`. Raised at M25's
implementation gate as a possible harmonization; escalated as an irreversible
exported-API decision and reviewed independently (RB01/RR01, now in
`reviews/archive/`). **Decision: keep the current names on every surface** —
`validity_pid5()` output columns, the `pid_items` keying columns, and
`pid_norms$scale` alike. The book's labels are recorded as provenance in
`SOURCES.md` and surfaced to users as an "also known as" note in the
documentation, never as a second naming scheme in the data.

Three grounds. The book is not a reliable naming authority even about itself: its
Appendix captions call *both* inconsistency tables VRIN, while Chapter 4 names the
100-item scale PID-5-INC-S. The primary sources favor `INC` — Keeley et al. (2016)
and Lowmaster et al. (2020) are both titled "Response Inconsistency Scale", and
Lowmaster's PID-5-INC-S treats `INC` as the parent stem, a lineage the package's
`INC`/`INCS` pair encodes and a `VRIN`/`INCS` pair would sever. And no rename of the
pair is simultaneously consistent with the book, the development papers, and that
lineage, so harmonization has no reachable end state.

The general rule this settles, beyond the one scale: **authority is per-content-type,
not per-document.** The book is the primary source for its own normative tables and is
cited as such (IP2, IP3); for the identity and name of a scale it did not develop, the
development paper is primary and the book is a secondary description — regardless of
its authors having created the instrument itself. An exported alias dataset mapping
book names to columns was considered and rejected (GP3, GP4): two documentation
sentences do the same work without a permanent exported surface.

If a future maintainer overrules this, RR01 records the path — one release, all
surfaces at once, NEWS entry, no dual columns and no `lifecycle` (GP2 licenses a
signature break outright; `lifecycle` is for functions and arguments, not output
column names, and is not a current Import).

### D-013 (2026-07-16): Adopt design principles IP1–IP4 / GP1–GP4 from the design interview

**Context:** The cairn migration left DESIGN.md rich on architecture but without formalized principles. The `/design-interview` elicited audience, boundary, governance, distribution, entry-bar, and dependency facts (Phase 1, commit c94f7db), banked nine candidates, and added history-mined and domain-derived ones in Phase 2.
**Decision:** Adopt four inviolables — IP1 instrument content sacrosanct (scope: item text and generated artifacts included), IP2 ground-truth oracles (scope: shipped numeric constants included), IP3 no scoring without an authoritative key / no norms without published tables, IP4 scores-never-judgment (line: cited-threshold flags in, generated interpretive prose out) — and four guiding principles: GP1 published rules win defaults, GP2 scored output never changes silently, GP3 researcher-first ergonomics, GP4 lean base-R core with family-earned Imports. **Consequences:** Milestone plans can cite "touches IPn/GPn"; changing an IP requires a new D-entry; the trailing-periods class of item-text change now formally requires source verification (IP1); norms work inherits the IP2/IP3 bars before it begins.

### D-016 (2026-07-16): Build-date versioning + checksum-locked manifest for distributed artifacts

**Context:** Committed `inst/extdata/` artifacts are distributed via raw/main links on the pkgdown download pages; the M19 QSF rebuild changed a file at a stable URL with no user-visible version signal, and filenames carried the instrument version (`_1.0_`) inconsistently while identifying builds not at all.
**Decision:** (a) Artifact revisions are identified by **build date** (YYYY-MM-DD); the instrument version (the Society's/APA's "1.0") stays a separate concept. (b) A committed manifest dataset **`hitop_artifacts`** (`file`, `instrument`, `format`, `instrument_version`, `build_date`, `md5`, `changes`; one row per build, history kept) is the single source of truth; a test locks every committed artifact's checksum to its current manifest row, so no artifact changes without a version bump — GP2 extended to artifacts. (c) Stamps are embedded where the format allows: DOCX footer ("Generated YYYY-MM-DD · hitop X.Y.Z"), QSF `SurveyName`; the flat Qualtrics .txt and REDCap zips have no safe metadata slot and are covered by the manifest and download pages only. (d) **Filenames carry no version** — stable URLs, the latest build always at the same link; the old `_1.0_` URLs break once (accepted, Jeff 2026-07-16). (e) `tools::md5sum()`, not sha256 — change-detection needs no cryptographic strength and md5 costs zero new dependencies (GP4).
**Consequences:** Every future artifact regeneration must add a manifest row or tests fail; download pages render version history from the manifest; generator default `file` arguments drop `_1.0`; embedding the DOCX footer stamp is an IP1-sanctioned metadata addition (signed off at the M20 plan gate), never a license for content drift — the parse-and-compare tests must pass unchanged.

### D-020 (2026-07-30): `norm_pid5()` reconciles a shifted response coding per scale, including the validity scales; `validity_pid5()`'s cut scores stay deferred

**Context:** `pid_norms` mixes metrics. Domain and BF-total rows are item means; `INC`/`INCS` are sums of within-pair absolute differences; `ORS` is a count of items at the range maximum (`R/validity_pid5.R:153`); `PRD` is a 22-item raw sum. A user scoring on a shifted four-option coding (1–4 against the official 0–3) needs each reconciled to the official range before lookup, and a single per-item shift — the obvious reading of a scale-agnostic rescale — is right for the means and wrong for the other three. DESIGN Known issue #3 defers the parallel question for `validity_pid5()`'s cut scores pending maintainer sign-off.
**Decision:** `norm_pid5()` reconciles each named column by its own metric — item means shifted by `low`, `PRD` by `low × nItems`, `ORS` re-derived against the shifted maximum, `INC`/`INCS` left unchanged as already coding-invariant. Signed off by Jeff at the 2026-07-30 plan gate. No published source states these formulas, so each is documented in `@details` on its merits (GP1's "where no published rule exists" branch) and the adjustment is reported once via `cli::cli_alert_info()` naming which scales were adjusted and which were not. Rejected: reconciling only the mean-metric domains and returning `NA` for the four validity scales (discards a derivable conversion), and returning `NA` for every column on any non-official coding (discards the well-defined domain conversion too).
**Consequences:** This is a norming-lookup decision only. `validity_pid5()`'s cut scores keep their current behavior — a warning when `srange != c(0, 3)`, no auto-adjustment — and DESIGN Known issue #3 stays open, so a user on a shifted coding can receive a reconciled norm percentile and an unreconciled cut-score flag in the same session; M27's `@details` must say so. Closing issue #3 is separate work.

### D-021 (2026-07-30): The PID-5-BF total prorates independently of the five domains under `missing = "apa"` (resolves the behavior D-017 deferred; promotes M26-D1)

**Context:** D-017 added the PID-5-BF total but explicitly left "its behavior under `missing = "apa"`" to be resolved in M26, and Markon et al. (2024) state a computation rule for the total (p. 23) but no missing-data rule for it anywhere. Because `score_pid5()` applies `missing` per scale, the total's 25-item basis and a domain's 5-item basis reach the APA 25%-unanswered threshold at different points: the total drops at 7 unanswered, a domain at 2. M26 recorded the resolution as the milestone-local entry M26-D1; the maintainer directed at the M26 merge gate (2026-07-30) that it be promoted here, since D-017 raised the question as a cross-cutting one.
**Decision:** The total is scored as its own 25-item scale and prorates independently of the domains — no special case couples them. GP1 governs: the book's stated computation is the published rule and takes the default, and the alternative would impose a coupling the source does not ask for. Rejected: blanking the total whenever any domain blanks (internally tidier profiles, but a deviation from the published rule with no source behind it), and blanking it only when every domain blanks (unreachable — see below).
**Consequences:** A total can be reported beside as many as **3 `NA` domains** (6 unanswered, two in each of three domains). The converse cannot occur: blanking all five domains needs 10 unanswered items, and the total drops at 7 — so "all five domains `NA` beside a reported total" is impossible, and the reverse case (an `NA` total beside reported domains) is reachable at 7+ unanswered. Documented in `score_pid5()`'s `@details`, `cairn/SOURCES.md` ("Note on the BF total score"), and NEWS; covered by tests at the 6/7-unanswered boundary. This governs the norming lookup M27 builds on: a scored total that is `NA` has no T score to convert, independently of its domains. Supersedes M26-D1, whose stated reason for staying milestone-local no longer holds.

### D-022 (2026-07-30): Norming functions return published cells only — no constant fitted from a norms table ships (from RR02; extends IP2/IP3 across the norming family)

**Context:** RR02 established that the 16 domain/total tables of Markon et al. (2024) are exact linear renderings of `raw = M + (T − 50)/10 × SD` at 2-dp rounding — 844 of 850 printed non-zero cells reproduce exactly — while the book prints M and SD nowhere. The generator is therefore recoverable by regression from the shipped data, which raised whether `norm_pid5()` may return a between-rows T by inverting that line instead of selecting a printed row. The question generalizes: the HiTOP-SR/BR source workbooks that arrived 2026-07-30 carry sample descriptives rather than lookup tables, so the same temptation will recur with a *better* excuse.
**Decision:** Every T score and percentile a norming function returns is a value printed in a shipped normative table, selected by arithmetic on printed cells only. No constant derived by fitting a shipped norms table — mean, SD, slope, intercept, or equivalent — ships in package code, package data, or a documented formula. Fitting is licensed at test time only, as IP2's "independent recomputation": constants derived inside a test from the shipped rows never touch a returned value. Rejected: shipping the fitted parameters (returned numbers would trace to a regression run in this repo rather than to a cited authority, failing IP2 directly and IP3 in spirit — the norms applied would be a reconstruction of the tables' generator, not the tables), and interpolating between printed rows (manufactures resolution the source does not print, with no oracle able to check it).
**Consequences:** Binds the whole norming family, not only PID-5 — a future SR/BR norming milestone working from descriptives rather than tables must publish a table or escalate, not fit one here. Costs a little accuracy at knife-edge midpoints, where RR02 found nearest-row and rounded inversion agree to within the tables' own 2-dp rounding anyway, and where the printed table is the more authoritative of the two. Does not touch D-020's `srange` reconciliation, whose per-scale formulas are coding-metric derivations rather than anything read off `pid_norms`.

### D-023 (2026-07-30): `ORS` is coding-invariant and is not rescaled — correcting D-020's four-formula partition to two adjustments and three no-ops

**Context:** D-020 decided that `norm_pid5()` reconciles a shifted response coding per scale, listing four treatments: "item means shifted by `low`, `PRD` by `low × nItems`, `ORS` re-derived against the shifted maximum, `INC`/`INCS` left unchanged as already coding-invariant". A fresh-context criteria audit at the 2026-07-30 M27/M28 split gate found the `ORS` clause unperformable on two independent grounds. `R/validity_pid5.R:153` computes `ORS` as `rowSums(data_items[, ors_items, drop = FALSE] == srange[[2]])` — a count of items sitting at the *actual* range maximum — so a pure shift leaves the same items at the maximum and the score unchanged, exactly like `INC`/`INCS`. And `norm_pid5()` receives scored columns rather than item data, so it could not re-derive a count against any maximum even if the score did vary.
**Decision:** The reconciliation is two adjustments and three no-ops: item means shifted by `low`, `PRD` by `low × nItems`, and `INC`, `INCS`, and `ORS` left unchanged as coding-invariant. Supersedes D-020's `ORS` clause only; every other part of D-020 — reconciling per scale rather than per item, including the validity scales rather than blanking them, documenting the formulas on their merits under GP1, and reporting the adjustment rather than making it silently — stands unchanged. Rejected: implementing the `ORS` branch as a no-op while the record still called it a re-derivation (the record would say one thing and the code another), and escalating all four formulas to a second review (the `ORS` finding is a plain reading of one line of code, not a judgment call — though the `PRD` and item-mean formulas remain independently unverified, which M28 AC5's hand-computed fixtures are what finally checks).
**Consequences:** M28 plans to the corrected partition: AC2 names two adjustments and three invariants, AC3 documents each and traces `ORS`'s invariance to its line of code, and AC5 tests the two adjusted metrics with hand-computed fixtures and asserts the three invariants are untouched. D-020's own `@details` obligation moves with the work from M27 to M28. If `ORS` is ever redefined as something other than a count at the range maximum, this entry stops holding and the treatment returns to open.

### D-024 (2026-07-30): `norm_pid5()`'s shifted-coding reports are `cli::cli_warn()` conditions, not `cli_alert_info()` messages — annotates D-020's reporting-mechanism clause

**Context:** D-020 specified that the per-scale reconciliation "is reported once via `cli::cli_alert_info()` naming which scales were adjusted and which were not". D-023 superseded D-020's `ORS` clause only and left every other clause standing, this one included. A fresh-context criteria audit at the 2026-07-30 M27/M28 split gate found that `cli_alert_info()` emits a message carrying no condition class, so no test can assert on it and neither `tryCatch()` nor `suppressWarnings()` can reach it — while `validity_pid5()` already emits `cli::cli_warn()` on exactly the same shifted-coding input (`R/validity_pid5.R:92`). M28 shipped `cli_warn()` for both the reconciliation report and the option-count refusal, recording the choice only in its work log; M28's review found `DECISIONS.md` still saying otherwise and routed it to the maintainer, who directed this entry at the merge gate.
**Decision:** Both shifted-coding reports `norm_pid5()` emits — the reconciliation report and the non-four-option refusal — are `cli::cli_warn()` conditions. Annotates D-020's reporting-mechanism clause; every other part of D-020 that D-023 left standing continues to stand. Rejected: `cli_alert_info()` as D-020 wrote it (not a catchable condition, so M28 AC5's tests could not assert the report at all and a user could not suppress it selectively), and splitting the two reports across mechanisms so that no single suppression call silences the function's coding messages.
**Consequences:** `norm_pid5()` now mixes condition classes — its two coding reports warn, while the pre-existing uncovered-scale and capping reports stay `cli_alert_*` messages — so `suppressWarnings()` silences the first pair and `suppressMessages()` the second, and a vignette chunk wanting silence needs both. That split is logged as an M28 sub-threshold review finding, not resolved here; unifying the function's four reports onto one mechanism is separate work. This does not make warning-class the repo default: DESIGN's `cli_alert_warning()` + `cli_alert_info()` convention still governs count-of-flagged-observations reporting, and the carve-out is for conditions a caller is expected to catch or suppress.

### D-025 (2026-07-31): All four of `norm_pid5()`'s reports are `cli::cli_warn()` conditions, so one `suppressWarnings()` silences the function (annotates D-024's count-of-flagged-observations clause)

**Context:** D-024 made `norm_pid5()`'s two shifted-coding reports `cli_warn()` conditions and named the consequence it left open: the pre-existing uncovered-scale and capping reports stayed `cli_alert_*` messages, so `suppressWarnings()` silenced one pair and `suppressMessages()` the other, and it recorded that "unifying the function's four reports onto one mechanism is separate work". That work is M29. The same entry also held that "DESIGN's `cli_alert_warning()` + `cli_alert_info()` convention still governs count-of-flagged-observations reporting" — and M29's fresh-context criteria audit found the capping report is literally such a count (`{n_low} observation{?s} below and {n_high} above ... were capped`), so the only D-024-compatible unification crosses that clause.
**Decision:** All four reports `norm_pid5()` emits — the option-count refusal, the reconciliation report, the uncovered-scale report, and the capping report — are `cli::cli_warn()` conditions, so a single `suppressWarnings()` silences the whole function. Annotates D-024's convention clause, narrowing it: the clause governs a count of observations *flagged for the caller's action* — `validity_pid5()`'s screening output, which pairs each count with an actionable `dplyr::filter()` remedy — and not a count reporting what the function did to its own return value. D-024's decision paragraph stands unchanged. Rejected: adding a `quiet` argument to `norm_pid5()` (silences all four in one call without touching any condition class, but widens the exported signature and leaves the split for anyone using the standard suppressors), and documenting the split without fixing it (cheapest, no behavior change, but leaves a function no single call can silence).
**Consequences:** A caller who today silences `norm_pid5()`'s coverage or capping output with `suppressMessages()` will see warnings instead and must switch to `suppressWarnings()`; the package is pre-1.0 (0.2.0) and the maintainer waived a deprecation cycle at the M29 plan gate. NEWS records it. The uncovered-scale report was never inside the disputed clause — it counts columns, not observations. DESIGN's alert convention is otherwise untouched and still governs `validity_pid5()`.

### D-026 (2026-07-31): `prefix` is matched literally wherever this package strips it from a column name, in `rank_scales()` as well as `norm_pid5()`

**Context:** Both functions recover a scale name by stripping `prefix` with `sub(paste0("^", prefix), ...)`, which compiles the user's string as a regular expression. M29's investigation confirmed two failure modes: a `prefix` containing `(` aborts with `invalid regular expression '^pid(_'`, naming a regex the user never wrote, and a `prefix` containing `.` matches a character it should not, stripping a prefix that was never there. `rank_scales()`'s roxygen (`R/rank_scales.R:15-17`) documents the regex behavior deliberately, so for that function this is a documented-behavior change rather than a plain bug fix.
**Decision:** `prefix` is a literal string everywhere this package strips it, in `rank_scales()` as well as `norm_pid5()`, and `rank_scales()`'s roxygen stops promising regex semantics. Rejected: fixing `norm_pid5()` alone and carrying `rank_scales()` as a candidate row — one argument name meaning literal in one exported function and regex in another is a divergence a later milestone would have to close anyway, and the two call sites are three lines apart in shape.
**Consequences:** A caller passing a regex-bearing `prefix` to `rank_scales()` and relying on it to match loses that behavior; a caller passing a metacharacter-bearing literal prefix to either function stops getting a cryptic regex error or a wrongly stripped name. Under GP2 the change is NEWS-flagged. This says nothing about `prefix` where it is only *pasted onto* a name (`score_engine()`, the `label_*` family) — those were never regex and are untouched.

### D-027 (2026-07-31): The 25 PID-5 facets are normed for the full and short forms, and the book's unattainable printed rows ship verbatim

**Context:** `pid_norms` shipped seven of the Appendix's twelve tables at M25; A–6 (p. 124) and A–8 (p. 151) norm all 25 facets ("trait scales" in the book's wording) for the 220-item and 100-item forms, and were carried as a ROADMAP candidate. Until now `norm_pid5()` returned `NA` in both conversion columns for any facet, with a warning naming it as uncovered — the behavior `?norm_pid5`, both vignettes, and four tests were written around. Ingesting the two tables also surfaced a property the domain tables mostly lack: a facet score is a mean of items coded 0–3 and so stops at 3.00, yet 42 of the 50 facet columns print raws above 3.00, and 19 of them clamp at exactly 4.00 and repeat it across up to 12 consecutive T rows (short-form anxiousness, T = 89–100).
**Decision:** Two parts. (1) The 25 facets are normed for `FULL` and `SF`: `pid_norms` gains 3,550 rows over 50 (version, scale) pairs, the facet stems join `norm_engine.R`'s item-mean partition, and `norm_pid5()` returns a real `_t` and `_ptl` for every facet on those two versions instead of `NA` plus a warning. This is a GP2 change to scored output and is NEWS-flagged. (2) Every printed row ships as published, the unattainable ones included, and is read by the function's ordinary nearest-row rule with the toward-50 tie-break (D-022, RR02) unchanged — which returns the *lowest* T of a ceiling run, mirroring what the floor run already did at the other end. Rejected: truncating each facet column at raw 3.00, which would shift a maximum scorer's T down by one point on 18 of the 50 columns by this package's edit rather than by the book's tabulation, and would make `pid_norms` a filtered view of the source rather than the source (IP3).
**Consequences:** Code relying on a facet coming back `NA` from `norm_pid5()` on the full or short form now gets a value, and the uncovered-scale warning no longer fires for facets; `SD-TD`, `PNA`, and any facet on the brief form remain uncovered and are what the re-pointed tests now use. `norm_mean_scales` spells the 25 stems out rather than reading `pid_scales` at namespace-load time, with a test holding the two sets in step and the `data-raw/norms_pid5.R` build refusing any caption→stem map not `setequal()` to the version's facets. The `lm`-based linearity test could not survive the widened data — 20 of the 50 new columns exceed its bound — and is replaced by an exact minimax (Chebyshev) line fitted inside the test over each column's interior span, asserting 0.005, half a unit in the last printed place; the line never ships (D-022). Whether the 4.00 clamp is a deliberate tabulation choice or an erratum is unresolved and recorded as an open question against the source in `cairn/references/markon2024.md`; a 4.00 ceiling is what a 1–4 coding would produce, so it is worth putting to the authors.
