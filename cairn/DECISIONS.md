### D-040 (2026-08-24): `write_module()` writes a module's `item_order` attribute as the file's `itemOrder` (annotates D-039's reserved-slot clause under D-039(d); promotes M055-D1)

**Context:** D-039(a) reserved `itemOrder` for a shuffled form's printed order and its appended Classes paragraph recorded that `read_module()` returns it on the module's `item_order` attribute, while M054 shipped `write_module()` documented as never writing the field. A descriptor read and written again therefore lost the printed order it recorded, and M055's `descriptor` argument on the three HiTOP-SR generators would have needed a private writer to save one. D-039(d) makes the format's fields a public contract that changes "only through a further D-entry", so the reversal cannot stay milestone-local: with M055-D1 recorded only in its milestone file, the canonical log described a format the package no longer writes.

**Decision:** `write_module()` writes `itemOrder` whenever the module carries an `item_order` attribute, after checking that the attribute is a permutation of the module's items rather than trusting it; a module carrying no such attribute still writes no field. The generators set the attribute — only `generate_docx_hitopsr(randomize = TRUE)` has a printed order to set — and the sidecar writer sets it unconditionally so a `NULL` order clears one an incoming module already carried. Nothing else about the format changes: the field's definition, the required-field set, and the `"1.0"` version string are untouched, so D-039's contract is annotated rather than reopened. Decided by Jeff at the 2026-08-24 M055 review gate; rejected: leaving the decision milestone-local (cheapest, but D-039(d) requires a D-entry and the log would stay wrong about the shipped format).

**Consequences:** Saving and reading a descriptor are symmetric — a file read and written again keeps its recorded order. One paragraph of `?write_module` is rewritten, and a hand-set `item_order` that is not a permutation of the module's items is now an error at write time rather than at read time. `read_module()`'s `hitop_module_file_bad_item_order` class and every other condition D-039's Classes paragraph lists are unchanged. The evidence that would reopen this is a caller needing to write a descriptor while deliberately dropping a printed order the module carries, which today requires clearing the attribute first.

### D-039 (2026-08-24): A module is saved as a versioned JSON descriptor whose keying is rebuilt from the package's own tables on read, and {jsonlite} moves to Imports (applies IP1 and IP2 to a new file format; extends GP4's dependency posture on the D-035 precedent)

**Context:** Scoring module-collected HiTOP-SR data requires rebuilding the module, which today means retyping every scale name into `hitop_module()` — the whole list, months after the form was fielded, with a typo scoring the wrong scales and a forgotten scale scoring none. A file written beside the generated Qualtrics/REDCap/Word export and read back at scoring time removes that, but it raises two questions the package has not faced: what format a researcher-held descriptor takes, and how much of what the file says the package is willing to believe.

**Decision:** (a) The format is **JSON**, carrying a `format` version string, the writing package version and build date (the D-016 spirit), the instrument, the scale names, the item numbers, and a reserved `itemOrder` slot for a shuffled form's printed order. (b) **{jsonlite} moves from Suggests to Imports.** The browser module builder runs under webR and installs no Suggests, so a Suggests-guarded writer could not run there at all, which is the same reasoning D-035 accepted for {zip}; a module descriptor is a family, not one function (GP4). (c) **The file never supplies keying.** `read_module()` rebuilds items and reverse flags by passing the file's scale names through `hitop_module()`, so the package's own tables remain the only source of scale membership (IP1); the file's recorded `items` and `nItems` are cross-checked against that rebuild and any disagreement is a classed error, never a silent preference for either side. (d) The format's fields and its version string are a public contract on the terms D-034(c) set for condition classes: they change only through a further D-entry, and the condition classes M054 introduces are appended to this entry when it implements them. Chosen by Jeff at the 2026-08-24 M054 plan gate over base-R DCF (rejected: R-specific, unreadable by any other tool a researcher has), RDS (rejected: opaque binary a researcher cannot inspect, and it would carry stale keying), and a bare CSV of scale names (rejected: no version, no room to grow).

**Consequences:** The package gains one Import; {jsonlite} is already declared in Suggests for QSF verification (D-015), so no new dependency tree enters, and D-015's Suggests rationale is superseded on the declaration but not on its use. M054 ships the format and `write_module()`/`read_module()`; M055 gives the three HiTOP-SR generators a `descriptor` argument and populates `itemOrder`; M056 puts the download on the builder page, which is what finally closes DESIGN known issue 8. A descriptor written by an older package version whose scale tables have since moved fails loudly on the cross-check rather than scoring quietly, which is the intended behavior under IP1 and GP2. The evidence that would reopen (b) is {jsonlite} failing to build under emscripten, which would return the format to the base-R DCF option; the evidence that would reopen (c) is a legitimate workflow needing an old descriptor to score against tables that have changed.

**Classes (appended 2026-08-24 by M054, per (d) above):** The format version string this release writes is `"1.0"`. The file's fields are `format`, `package`, `packageVersion`, `buildDate`, `instrument`, `scales`, `items`, `nItems`, and the reserved `itemOrder`; `format`, `instrument`, and `scales` are required and drive the rebuild, `items` and `nItems` are cross-checked against it, and the rest are recorded for the reader and ignored on read, so a written file reads back to an object identical to the module written. `read_module()` raises seven classed conditions, each naming the file: `hitop_module_file_missing` (no file at the given path), `hitop_module_file_invalid_json` (the file does not parse as JSON), `hitop_module_file_missing_field` (a required field is absent), `hitop_module_file_unsupported_format` (the `format` value is not a version string, or names a version later than this release writes), `hitop_module_file_unknown_scales` (the file's instrument or scale names are ones `hitop_module()` refuses, raised with that refusal as its parent), `hitop_module_file_items_mismatch` (the recorded `items` or `nItems` disagrees with the rebuild), and `hitop_module_file_bad_item_order` (`itemOrder` is present but is not a permutation of `items`).

### D-038 (2026-08-23): A browser-builder control that only reaches an already-gated generator argument is page behavior, not an artifact-touching change under IP1 (applies IP1 to the web-app control family; reads the return-to-the-gate clauses D-036 and D-037 each closed with)

**Context:** D-036 and D-037 each authorized one change to a generated Word form and each closed by requiring that "the next artifact-touching change returns to the gate". The browser module builder is now growing controls that expose generator arguments those gates already created and signed off — M049's `renumber`, and M050's queued online-export arguments. Read literally, every such control could be argued to touch a participant-facing artifact, which would put a gate in front of each one; read loosely, the app could become a route around IP1. Neither reading is right, and the question was escalated to an outside review at M049's implementation gate.

**Decision:** A control on the builder page that does no more than let a visitor choose among values of a generator argument the maintainer has already signed off is page behavior and needs no fresh IP1 sign-off. Every document such a control can produce is one the package already produces for an R caller, so no printed token, item, response option, or administration instruction moves. Two things stay outside this: an argument whose values were never gated, and any change to what the generator prints for a given set of arguments — both return to the gate as D-036 and D-037 require. The page's own copy — notices, labels, the README — is researcher-facing and outside IP1's scope, which names participant-facing text.

**Consequences:** M049 ships its numbering control, and M050's queued controls, without a further IP1 gate; the milestone files carry the per-control reasoning. This authorizes exposure of already-gated arguments and establishes no carve-out for anything else: a builder control that would change generated content, rather than select among gated behaviors, is an artifact-touching change and returns to the gate. Recorded from RR03 (`cairn/reviews/archive/RR03-builder-word-numbering-control.md`, question 5), which reached this on the materials M049's brief supplied. The evidence that would reopen it is a builder control found to produce a document no signed-off argument combination produces.

### D-037 (2026-08-23): A Word form built from a module is titled "HiTOP-SR Module", the instrument's name plus what the form is (applies IP1 to the header line D-036 left standing)

**Context:** `generate_docx_hitopsr()` prints one fixed header, `title = "HiTOP-SR (v1.0)"` (`R/generate_docx.R:164`, rendered at `R/generate_docx.R:512`), whatever the form contains — so a two-scale module form is headed as the full 405-item instrument, which is what Jeff raised on 2026-08-23 from the browser builder's output. The header is participant-facing text, which IP1 puts behind maintainer sign-off and holds is "a sourced content change, not a style fix"; D-036 closed by requiring that "the next artifact-touching change returns to the gate", exactly as D-028 had required of it.

**Decision:** A module form's header names the instrument and then says what the document is — `"HiTOP-SR Module (v1.0)"` — where a full-instrument form keeps `"HiTOP-SR (v1.0)"`, signed off by Jeff at the 2026-08-23 M048 plan gate, which is the IP1 sign-off for the wording. The instrument's own name, item text, response options, and administration instructions are untouched; the added word describes the artifact, not the instrument, and matches the vocabulary D-034 settled and the builder app's own name. The sign-off is bounded by machine check rather than by assertion: M048's AC3 rebuilds the full instrument at both paper sizes and compares each against its committed `inst/extdata/hitopsr_*.docx`, so an unconditional rename fails the gate, and AC1 pins both defaults by parsing the header back out of a built document. Rejected at the gate: the web app passing `title` itself with the package unchanged (declined — an R caller building a module would still get a form headed as the full instrument), and escalating to an outside review brief before planning (offered as the scope touches an inviolable principle; declined as disproportionate to a label naming the document).

**Consequences:** `generate_docx_hitopsr(title = )` gains a `NULL` sentinel resolving by whether `module` is supplied; an explicit `title` is honored unchanged, so no caller's output moves without asking. No shipped artifact under `inst/extdata/` changes and no `hitop_artifacts` row moves, because every distributed form is the full instrument. The change is recorded in NEWS per GP2. This authorizes the module header line and establishes no general carve-out from IP1 — the next artifact-touching change returns to the gate. The evidence that would reopen it is the Society naming a partial administration of the HiTOP-SR something other than a module.

### D-036 (2026-08-21): An item's printed number on a module Word form is a positional label, not instrument content — module forms renumber 1..n by default (applies IP1 to the case D-028 left open; the online exports are deliberately excluded)

**Context:** `apply_module()` reduces the item table without rewriting numbering (`R/module.R:130-132`), so a four-scale HiTOP-SR module Word form prints the full instrument's gapped numbers — 7, 42, 213 — which reads as an error to a participant and is what Jeff raised on 2026-08-21 from the browser builder's output. IP1 puts generated DOCX artifacts behind maintainer sign-off and holds that "a change to participant-facing text is a sourced content change, not a style fix". D-028 blessed one layout change on the PID forms and explicitly bounded itself: "This authorizes one layout change and establishes no general style-fix carve-out from IP1: the next artifact-touching change returns to the gate." This is that next change, and unlike D-028's line break it alters a printed token rather than only where a line wraps.

**Decision:** A module form's item numbers are positional labels for the person filling in the page, not instrument content, and `generate_docx_hitopsr(module =)` renumbers them `1..n` by default — signed off by Jeff at the 2026-08-21 M046 plan gate, which is the IP1 sign-off for the change. Item text, response options, and administration instructions are untouched, and the sign-off is bounded by machine check rather than by assertion: M046's AC1 compares every printed row's text against `hitopsr_items` derived independently of the module descriptor, and its AC3 compares a fresh default full-instrument build against the committed `inst/extdata/hitopsr_US.docx` row for row, so wording drift or an unconditional renumber fails the gate. Renumbering also makes the printed number equal the column position `score_hitopsr(module =)` already addresses items by (`R/module.R:230-236`), so the paper form and the scoring API stop disagreeing. Rejected at the gate: escalating to an outside review brief before planning (offered as the scope touches an inviolable principle; declined as disproportionate to a positional label), keeping original numbers behind an opt-in argument (declined — the browser builder would then need its own change before anyone saw the fix), and renumbering the Qualtrics and REDCap exports too (declined — there an item number names a collected data column, so renumbering would rename collected variables and diverge from dictionaries already in the field).

**Consequences:** `generate_docx_hitopsr()` gains `renumber` (default `TRUE`) and `randomize` (default `FALSE`); a shuffled form carries a printed new-number-to-original-number crosswalk on its scoring page so it is scoreable from the paper alone. The Word form and the two online exports now number a module differently on purpose, and each generator's help page says so. No shipped artifact under `inst/extdata/` changes, because every distributed form is the full instrument and already numbered `1..n`; no `hitop_artifacts` row moves. This authorizes renumbering on module forms and establishes no general carve-out from IP1 — the next artifact-touching change returns to the gate, exactly as D-028 required of this one. The evidence that would reopen it is a report of module data collected on a pre-M046 form being scored against a renumbered key.

### D-035 (2026-08-21): The REDCap generators build their archive with {zip} rather than `utils::zip()`, adding {zip} to Imports (extends GP4's dependency posture; unblocks M045's in-browser build)

**Context:** `build_redcap_zip()` and its HiTOP-HSUM sibling wrote their archive with `utils::zip()`, which does not implement the zip format — it shells out to an external `zip` executable via `system2()`. M045's feasibility probe found that call aborts under WebAssembly with "The `system()` function is unsupported under Emscripten.", so the REDCap format could not be generated in the browser at all, while Qualtrics and DOCX both could. The same shell-out is a latent failure on any ordinary machine with no `zip` program on `PATH`, which is the common case on Windows; nothing in the package checks for one or reports its absence usefully.

**Decision:** Both call sites use `zip::zip(mode = "cherry-pick")`. {zip} implements the archive format in C with no child process, and its cherry-pick mode reproduces the flat entry naming that `utils::zip()`'s `-j` extra gave, so the archive REDCap receives is unchanged in shape. {zip} enters Imports. Chosen by Jeff at the 2026-08-21 M045 implementation gate over three alternatives: rebuilding the archive in the web app's own JavaScript (rejected — it copies the package's packaging logic into a second repo, where it can drift from the generator that produces the CSV it packs), shipping the app with only the two working formats (rejected — the page would silently do less than the milestone promised), and returning the milestone to plan (rejected — the format is generable, and the blocker is one call site).

**Consequences:** The package gains one Import. {zip} has no dependencies of its own and is already pulled in transitively by {officer}, so nobody who can install this package today acquires a new transitive tree. Generating a REDCap instrument no longer requires any external program, which is a user-visible improvement in its own right and is recorded in NEWS. Any future generator that needs to write an archive uses {zip}; a further `utils::zip()` call site reaching the package would reintroduce the emscripten failure. The evidence that would reopen this is {zip} ceasing to build under emscripten, which would return the REDCap format to the app-side or two-format options rejected above.

### D-034 (2026-08-21): A chosen set of an instrument's scales is a "module", and this package's condition classes are a public contract (applies GP3; extends GP4's dependency posture to deprecation machinery)

**Context:** `hitop_subset()` and the `subset` argument shipped in the unreleased 0.2.0 development version (M024, M037). Two problems surfaced when the vocabulary was reviewed for M043: `subset` shadows base R's `subset()` generic, and the word describes what is removed rather than what is administered, which reads badly on an instrument a researcher fields as a unit. The rename had to happen before modularization spreads to the HiTOP-BR and PID-5, or the generalization would inherit two vocabularies. Separately, M043's acceptance criteria required the deprecation warning and the both-arguments error to be asserted *by condition class*, because message text is prose that may be reworded; `cli_abort()`'s default `rlang_error` does not discriminate, so classes had to be introduced.

**Decision:** (a) The domain term is **module**: `hitop_module()`, a `module` argument, and `available_scales()` to browse what a module can be built from. Chosen by Jeff at the 2026-08-21 plan gate over changing only the prose (rejected: leaves the docs and the code speaking differently) and over renaming the function but not the argument (rejected: the mismatch stays visible at every call site). (b) `hitop_subset()` and `subset` remain as warning shims rather than being removed outright, even though 0.2.0 never shipped, because the development version is installed from GitHub and pak. (c) The four condition classes this milestone introduces — `hitop_deprecated_subset`, `hitop_both_module_args`, `hitop_unknown_instrument`, `hitop_unsupported_instrument` — are a **public contract**: tests assert on them, callers may catch them, and they are renamed only through a further D-entry. Message text carries no such promise. (d) The deprecation is hand-rolled with `cli::cli_warn()` rather than adopting {lifecycle} — one deprecation does not earn a dependency (GP4), and a dependency change needs its own gate.

**Consequences:** Every future exported condition this package raises deliberately for callers to catch is classed and named here or in a successor entry. The standing "Generalize modularization to BR/PID-5" candidate inherits the module vocabulary, not the subset one. The rename made `m = ` ambiguous between `module` and `missing` in `score_hitopsr()`, a break no shim can cover; it is recorded in NEWS. Two instrument-name collisions are accepted rather than resolved: base R's `subset()` no longer shadowed, but the HiTOP-HSUM's own Society name is the Harmful Substance Use *Module*, tracked as a ROADMAP candidate and barred from package-side resolution of the instrument's name by IP1. The evidence that would reopen (a) is the Society adopting a different term for the same concept.

### D-018 (2026-07-30): Validity-scale names follow the scale-development papers, not Markon et al. (2024) — `INC` is not renamed to `VRIN` (annotates D-017's M025/M026 norms arc)

The PID-5 book (Markon, Fossati, Somma & Krueger, 2024) calls Keeley's full-form
inconsistency scale "VRIN" where this package calls it `INC`. Raised at M025's
implementation gate as a possible harmonization; escalated as an irreversible
exported-API decision and reviewed independently (RB01/RR01, now in
`reviews/archive/`). **Decision: keep the current names on every surface** —
`validity_pid5()` output columns, the `pid_items` keying columns, and
`pid_norms$scale` alike. The book's labels are recorded as provenance in
`SOURCES.md` and surfaced to users as an "also known as" note in the
documentation, never as a second naming scheme in the data.

Three grounds. The book is not a reliable naming authority even about itself: its
Appendix captions call *both* inconsistency tables VRIN, while Chapter 4 names the
100-item scale PID-5-INC-S. The primary sources favor `INC` — Keeley et al. (2016)
and Lowmaster et al. (2020) are both titled "Response Inconsistency Scale", and
Lowmaster's PID-5-INC-S treats `INC` as the parent stem, a lineage the package's
`INC`/`INCS` pair encodes and a `VRIN`/`INCS` pair would sever. And no rename of the
pair is simultaneously consistent with the book, the development papers, and that
lineage, so harmonization has no reachable end state.

The general rule this settles, beyond the one scale: **authority is per-content-type,
not per-document.** The book is the primary source for its own normative tables and is
cited as such (IP2, IP3); for the identity and name of a scale it did not develop, the
development paper is primary and the book is a secondary description — regardless of
its authors having created the instrument itself. An exported alias dataset mapping
book names to columns was considered and rejected (GP3, GP4): two documentation
sentences do the same work without a permanent exported surface.

If a future maintainer overrules this, RR01 records the path — one release, all
surfaces at once, NEWS entry, no dual columns and no `lifecycle` (GP2 licenses a
signature break outright; `lifecycle` is for functions and arguments, not output
column names, and is not a current Import).

### D-013 (2026-07-16): Adopt design principles IP1–IP4 / GP1–GP4 from the design interview

**Context:** The cairn migration left DESIGN.md rich on architecture but without formalized principles. The `/design-interview` elicited audience, boundary, governance, distribution, entry-bar, and dependency facts (Phase 1, commit c94f7db), banked nine candidates, and added history-mined and domain-derived ones in Phase 2.
**Decision:** Adopt four inviolables — IP1 instrument content sacrosanct (scope: item text and generated artifacts included), IP2 ground-truth oracles (scope: shipped numeric constants included), IP3 no scoring without an authoritative key / no norms without published tables, IP4 scores-never-judgment (line: cited-threshold flags in, generated interpretive prose out) — and four guiding principles: GP1 published rules win defaults, GP2 scored output never changes silently, GP3 researcher-first ergonomics, GP4 lean base-R core with family-earned Imports. B3/B6/B9 (CRAN discipline, pre-CRAN breakage, deliberate 4.1 floor) remain prose facts in DESIGN's "Audience, boundary & governance", deliberately unnumbered.
**Consequences:** Milestone plans can cite "touches IPn/GPn"; changing an IP requires a new D-entry; the trailing-periods class of item-text change now formally requires source verification (IP1); norms work inherits the IP2/IP3 bars before it begins.

### D-014 (2026-07-16): HiTOP-HSUM source of truth and `other_drug_rule` design

**Consequences:** IP1 verification for HSUM traces to this sheet (provenance in SOURCES.md); future HSUM scoring work inherits it. Default REDCap output changes for other-drug symptom gating — acceptable pre-1.0, noted in NEWS.

### D-015 (2026-07-16): jsonlite added to Suggests for QSF verification

**Context:** M019 locks the committed Qualtrics QSF artifact to `hitophsum_items`/`hitophsum_choices` via a parse-and-compare test (the oracle pattern of the REDCap export tests). QSF is JSON; base R has no JSON parser, and regex extraction from a 65k-character single-line file is too fragile to serve as an IP2 oracle.
**Decision:** Add **jsonlite to Suggests** — test-only, guarded by `skip_if_not_installed("jsonlite")`. No Imports change; the maintainer API script's httr2 dependency stays out of DESCRIPTION entirely (devel/ is .Rbuildignore'd).
**Consequences:** The QSF verification test parses structure rather than text; contributors without jsonlite skip those tests. GP4's lean-Imports posture is preserved (Suggests, family-earned by the export-verification family).

### D-016 (2026-07-16): Build-date versioning + checksum-locked manifest for distributed artifacts

**Context:** Committed `inst/extdata/` artifacts are distributed via raw/main links on the pkgdown download pages; the M019 QSF rebuild changed a file at a stable URL with no user-visible version signal, and filenames carried the instrument version (`_1.0_`) inconsistently while identifying builds not at all.
**Decision:** (a) Artifact revisions are identified by **build date** (YYYY-MM-DD); the instrument version (the Society's/APA's "1.0") stays a separate concept. (b) A committed manifest dataset **`hitop_artifacts`** (`file`, `instrument`, `format`, `instrument_version`, `build_date`, `md5`, `changes`; one row per build, history kept) is the single source of truth; a test locks every committed artifact's checksum to its current manifest row, so no artifact changes without a version bump — GP2 extended to artifacts. (c) Stamps are embedded where the format allows: DOCX footer ("Generated YYYY-MM-DD · hitop X.Y.Z"), QSF `SurveyName`; the flat Qualtrics .txt and REDCap zips have no safe metadata slot and are covered by the manifest and download pages only. (d) **Filenames carry no version** — stable URLs, the latest build always at the same link; the old `_1.0_` URLs break once (accepted, Jeff 2026-07-16). (e) `tools::md5sum()`, not sha256 — change-detection needs no cryptographic strength and md5 costs zero new dependencies (GP4).
**Consequences:** Every future artifact regeneration must add a manifest row or tests fail; download pages render version history from the manifest; generator default `file` arguments drop `_1.0`; embedding the DOCX footer stamp is an IP1-sanctioned metadata addition (signed off at the M020 plan gate), never a license for content drift — the parse-and-compare tests must pass unchanged.

### D-017 (2026-07-30): Add a PID-5-BF total score to `score_pid5()` (a GP2 scored-output change, planned into M026)

**Context:** The PID-5-BF normative table the maintainer transcribed from the PID-5 book (`data-raw/norms_pid5bf_domains.csv`) norms a **total** score (`TOT_Raw`/`TOT_Ptl`, T 35–95) alongside the five domains, but `score_pid5(version = "BF")` returns only the five domains — so the normed total has nothing to convert. The M025 plan-gate criteria audit surfaced this as an unreachable state: satisfying it means adding a scale, which IP1 gates behind maintainer sign-off.
**Decision:** `score_pid5(version = "BF")` gains a total-score column (`prefix` + `total`), signed off by Jeff at the 2026-07-30 plan gate. It is implemented in **M026**, not M025 — M025 stays data-only and ships the TOT rows in `pid_norms`. The exact rule (item-level mean over all 25 items versus the mean of the five domain means, and its behavior under `missing = "apa"`) is resolved from the book at M026 T2 and traced in `cairn/SOURCES.md`; the two agree on complete data and diverge only under missingness. Rejected: shipping the TOT norm rows with no scorer (a norm with nothing to convert), and dropping the TOT rows (discards transcribed data the book publishes).
**Consequences:** BF scored output gains a column — a GP2 change, so it is NEWS-flagged and covered by a hand-computed oracle test; FULL/SF output is untouched. `pid_scales` gains a BF total entry, which is IP1 content and traces to a cited source before it ships (IP2). Downstream code that counts `score_pid5(version = "BF")` columns must migrate; acceptable pre-CRAN.

### D-019 (2026-07-30): The PID-5-BF total enters `pid_scales`, and its ripple into `reliability_pid5()` and the BF paper forms is accepted (extends D-017; re-points D-017's M026 task references after the M026/M027 split)

**Context:** D-017 signed off the BF total and noted that "`pid_scales` gains a BF total entry, which is IP1 content", but scoped its consequences to `score_pid5()`. The M026 plan-gate criteria audit found that `pid_scales[[version]]$itemNumbers` has three consumers, not one: `score_pid5()` (`R/score_pid5.R:107`), `reliability_pid5()` (`R/reliability_pid5.R:60`), and the printed scoring table of `generate_docx_pid5(version = "BF", include_scoring = TRUE)` (`R/generate_docx.R:1136`). The third is participant-facing artifact content, which IP1 gates behind maintainer sign-off and D-016 manifest-locks by md5, so adding the row would silently stale two committed DOCX artifacts.

### D-020 (2026-07-30): `norm_pid5()` reconciles a shifted response coding per scale, including the validity scales; `validity_pid5()`'s cut scores stay deferred

**Context:** `pid_norms` mixes metrics. Domain and BF-total rows are item means; `INC`/`INCS` are sums of within-pair absolute differences; `ORS` is a count of items at the range maximum (`R/validity_pid5.R:153`); `PRD` is a 22-item raw sum. A user scoring on a shifted four-option coding (1–4 against the official 0–3) needs each reconciled to the official range before lookup, and a single per-item shift — the obvious reading of a scale-agnostic rescale — is right for the means and wrong for the other three. DESIGN Known issue #3 defers the parallel question for `validity_pid5()`'s cut scores pending maintainer sign-off.
**Decision:** `norm_pid5()` reconciles each named column by its own metric — item means shifted by `low`, `PRD` by `low × nItems`, `ORS` re-derived against the shifted maximum, `INC`/`INCS` left unchanged as already coding-invariant. Signed off by Jeff at the 2026-07-30 plan gate. No published source states these formulas, so each is documented in `@details` on its merits (GP1's "where no published rule exists" branch) and the adjustment is reported once via `cli::cli_alert_info()` naming which scales were adjusted and which were not. Rejected: reconciling only the mean-metric domains and returning `NA` for the four validity scales (discards a derivable conversion), and returning `NA` for every column on any non-official coding (discards the well-defined domain conversion too).
**Consequences:** This is a norming-lookup decision only. `validity_pid5()`'s cut scores keep their current behavior — a warning when `srange != c(0, 3)`, no auto-adjustment — and DESIGN Known issue #3 stays open, so a user on a shifted coding can receive a reconciled norm percentile and an unreconciled cut-score flag in the same session; M027's `@details` must say so. Closing issue #3 is separate work.

### D-021 (2026-07-30): The PID-5-BF total prorates independently of the five domains under `missing = "apa"` (resolves the behavior D-017 deferred; promotes M026-D1)

**Context:** D-017 added the PID-5-BF total but explicitly left "its behavior under `missing = "apa"`" to be resolved in M026, and Markon et al. (2024) state a computation rule for the total (p. 23) but no missing-data rule for it anywhere. Because `score_pid5()` applies `missing` per scale, the total's 25-item basis and a domain's 5-item basis reach the APA 25%-unanswered threshold at different points: the total drops at 7 unanswered, a domain at 2. M026 recorded the resolution as the milestone-local entry M026-D1; the maintainer directed at the M026 merge gate (2026-07-30) that it be promoted here, since D-017 raised the question as a cross-cutting one.
**Decision:** The total is scored as its own 25-item scale and prorates independently of the domains — no special case couples them. GP1 governs: the book's stated computation is the published rule and takes the default, and the alternative would impose a coupling the source does not ask for. Rejected: blanking the total whenever any domain blanks (internally tidier profiles, but a deviation from the published rule with no source behind it), and blanking it only when every domain blanks (unreachable — see below).
**Consequences:** A total can be reported beside as many as **3 `NA` domains** (6 unanswered, two in each of three domains). The converse cannot occur: blanking all five domains needs 10 unanswered items, and the total drops at 7 — so "all five domains `NA` beside a reported total" is impossible, and the reverse case (an `NA` total beside reported domains) is reachable at 7+ unanswered. Documented in `score_pid5()`'s `@details`, `cairn/SOURCES.md` ("Note on the BF total score"), and NEWS; covered by tests at the 6/7-unanswered boundary. This governs the norming lookup M027 builds on: a scored total that is `NA` has no T score to convert, independently of its domains. Supersedes M026-D1, whose stated reason for staying milestone-local no longer holds.

### D-022 (2026-07-30): Norming functions return published cells only — no constant fitted from a norms table ships (from RR02; extends IP2/IP3 across the norming family)

**Context:** RR02 established that the 16 domain/total tables of Markon et al. (2024) are exact linear renderings of `raw = M + (T − 50)/10 × SD` at 2-dp rounding — 844 of 850 printed non-zero cells reproduce exactly — while the book prints M and SD nowhere. The generator is therefore recoverable by regression from the shipped data, which raised whether `norm_pid5()` may return a between-rows T by inverting that line instead of selecting a printed row. The question generalizes: the HiTOP-SR/BR source workbooks that arrived 2026-07-30 carry sample descriptives rather than lookup tables, so the same temptation will recur with a *better* excuse.
**Decision:** Every T score and percentile a norming function returns is a value printed in a shipped normative table, selected by arithmetic on printed cells only. No constant derived by fitting a shipped norms table — mean, SD, slope, intercept, or equivalent — ships in package code, package data, or a documented formula. Fitting is licensed at test time only, as IP2's "independent recomputation": constants derived inside a test from the shipped rows never touch a returned value. Rejected: shipping the fitted parameters (returned numbers would trace to a regression run in this repo rather than to a cited authority, failing IP2 directly and IP3 in spirit — the norms applied would be a reconstruction of the tables' generator, not the tables), and interpolating between printed rows (manufactures resolution the source does not print, with no oracle able to check it).
**Consequences:** Binds the whole norming family, not only PID-5 — a future SR/BR norming milestone working from descriptives rather than tables must publish a table or escalate, not fit one here. Costs a little accuracy at knife-edge midpoints, where RR02 found nearest-row and rounded inversion agree to within the tables' own 2-dp rounding anyway, and where the printed table is the more authoritative of the two. Does not touch D-020's `srange` reconciliation, whose per-scale formulas are coding-metric derivations rather than anything read off `pid_norms`.

### D-023 (2026-07-30): `ORS` is coding-invariant and is not rescaled — correcting D-020's four-formula partition to two adjustments and three no-ops

**Context:** D-020 decided that `norm_pid5()` reconciles a shifted response coding per scale, listing four treatments: "item means shifted by `low`, `PRD` by `low × nItems`, `ORS` re-derived against the shifted maximum, `INC`/`INCS` left unchanged as already coding-invariant". A fresh-context criteria audit at the 2026-07-30 M027/M028 split gate found the `ORS` clause unperformable on two independent grounds. `R/validity_pid5.R:153` computes `ORS` as `rowSums(data_items[, ors_items, drop = FALSE] == srange[[2]])` — a count of items sitting at the *actual* range maximum — so a pure shift leaves the same items at the maximum and the score unchanged, exactly like `INC`/`INCS`. And `norm_pid5()` receives scored columns rather than item data, so it could not re-derive a count against any maximum even if the score did vary.
**Decision:** The reconciliation is two adjustments and three no-ops: item means shifted by `low`, `PRD` by `low × nItems`, and `INC`, `INCS`, and `ORS` left unchanged as coding-invariant. Supersedes D-020's `ORS` clause only; every other part of D-020 — reconciling per scale rather than per item, including the validity scales rather than blanking them, documenting the formulas on their merits under GP1, and reporting the adjustment rather than making it silently — stands unchanged. Rejected: implementing the `ORS` branch as a no-op while the record still called it a re-derivation (the record would say one thing and the code another), and escalating all four formulas to a second review (the `ORS` finding is a plain reading of one line of code, not a judgment call — though the `PRD` and item-mean formulas remain independently unverified, which M028 AC5's hand-computed fixtures are what finally checks).
**Consequences:** M028 plans to the corrected partition: AC2 names two adjustments and three invariants, AC3 documents each and traces `ORS`'s invariance to its line of code, and AC5 tests the two adjusted metrics with hand-computed fixtures and asserts the three invariants are untouched. D-020's own `@details` obligation moves with the work from M027 to M028. If `ORS` is ever redefined as something other than a count at the range maximum, this entry stops holding and the treatment returns to open.

### D-024 (2026-07-30): `norm_pid5()`'s shifted-coding reports are `cli::cli_warn()` conditions, not `cli_alert_info()` messages — annotates D-020's reporting-mechanism clause

**Context:** D-020 specified that the per-scale reconciliation "is reported once via `cli::cli_alert_info()` naming which scales were adjusted and which were not". D-023 superseded D-020's `ORS` clause only and left every other clause standing, this one included. **Decision:** Both shifted-coding reports `norm_pid5()` emits — the reconciliation report and the non-four-option refusal — are `cli::cli_warn()` conditions. Rejected: `cli_alert_info()` as D-020 wrote it (not a catchable condition, so M028 AC5's tests could not assert the report at all and a user could not suppress it selectively), and splitting the two reports across mechanisms so that no single suppression call silences the function's coding messages.

### D-025 (2026-07-31): All four of `norm_pid5()`'s reports are `cli::cli_warn()` conditions, so one `suppressWarnings()` silences the function (annotates D-024's count-of-flagged-observations clause)

**Context:** D-024 made `norm_pid5()`'s two shifted-coding reports `cli_warn()` conditions and named the consequence it left open: the pre-existing uncovered-scale and capping reports stayed `cli_alert_*` messages, so `suppressWarnings()` silenced one pair and `suppressMessages()` the other, and it recorded that "unifying the function's four reports onto one mechanism is separate work". **Decision:** All four reports `norm_pid5()` emits — the option-count refusal, the reconciliation report, the uncovered-scale report, and the capping report — are `cli::cli_warn()` conditions, so a single `suppressWarnings()` silences the whole function. ### D-026 (2026-07-31): `prefix` is matched literally wherever this package strips it from a column name, in `rank_scales()` as well as `norm_pid5()`

### D-027 (2026-07-31): The 25 PID-5 facets are normed for the full and short forms, and the book's unattainable printed rows ship verbatim

**Context:** `pid_norms` shipped seven of the Appendix's twelve tables at M025; A–6 (p. 124) and A–8 (p. 151) norm all 25 facets ("trait scales" in the book's wording) for the 220-item and 100-item forms, and were carried as a ROADMAP candidate. Until now `norm_pid5()` returned `NA` in both conversion columns for any facet, with a warning naming it as uncovered — the behavior `?norm_pid5`, both vignettes, and four tests were written around. Ingesting the two tables also surfaced a property the domain tables mostly lack: a facet score is a mean of items coded 0–3 and so stops at 3.00, yet 42 of the 50 facet columns print raws above 3.00, and 19 of them clamp at exactly 4.00 and repeat it across up to 12 consecutive T rows (short-form anxiousness, T = 89–100).
**Decision:** Two parts. (1) The 25 facets are normed for `FULL` and `SF`: `pid_norms` gains 3,550 rows over 50 (version, scale) pairs, the facet stems join `norm_engine.R`'s item-mean partition, and `norm_pid5()` returns a real `_t` and `_ptl` for every facet on those two versions instead of `NA` plus a warning. (2) Every printed row ships as published, the unattainable ones included, and is read by the function's ordinary nearest-row rule with the toward-50 tie-break (D-022, RR02) unchanged — which returns the *lowest* T of a ceiling run, mirroring what the floor run already did at the other end. Rejected: truncating each facet column at raw 3.00, which would shift a maximum scorer's T down by one point on 18 of the 50 columns by this package's edit rather than by the book's tabulation, and would make `pid_norms` a filtered view of the source rather than the source (IP3).
**Consequences:** Code relying on a facet coming back `NA` from `norm_pid5()` on the full or short form now gets a value, and the uncovered-scale warning no longer fires for facets; `SD-TD`, `PNA`, and any facet on the brief form remain uncovered and are what the re-pointed tests now use. `norm_mean_scales` spells the 25 stems out rather than reading `pid_scales` at namespace-load time, with a test holding the two sets in step and the `data-raw/norms_pid5.R` build refusing any caption→stem map not `setequal()` to the version's facets. The `lm`-based linearity test could not survive the widened data — 20 of the 50 new columns exceed its bound — and is replaced by an exact minimax (Chebyshev) line fitted inside the test over each column's interior span, asserting 0.005, half a unit in the last printed place; the line never ships (D-022). Whether the 4.00 clamp is a deliberate tabulation choice or an erratum is unresolved and recorded as an open question against the source in `cairn/references/markon2024.md`; a 4.00 ceiling is what a 1–4 coding would produce, so it is worth putting to the authors.

### D-032 (2026-08-13): A peer-reviewed instrument paper's descriptive table clears IP3's published-source bar where a development workbook does not — HiTOP-SR score intervals ship against it (applies IP2/IP3; narrows the 2026-08-06 ROADMAP correction)

The PID-5 has published norms but no reliability figure anywhere in the ingested source, so it cannot take an interval at all. The HiTOP-SR has the opposite gap: no norms, but Table 1 of its introduction paper prints alpha, mean, and SD per scale in one development sample (N = 780 in the 2026-03-24 tracked-changes draft — observed 2026-08-13, and the final submitted version is not yet in hand). Placing a person against that table's mean and expressing the interval in its SD units is norm-referencing in substance, so it meets IP3 head-on: "norming functions ship only against published, citable normative tables".

**Decision:** A descriptive table in a peer-reviewed instrument paper is a published, citable source for reference statistics under IP3, and `interval_hitopsr()` (M041) ships against the HiTOP-SR introduction paper's Table 1. Two conditions bind it. First, the reference group is named as the paper's development sample, with its N, wherever the numbers surface — help page, NEWS, pkgdown, vignette — and an acceptance criterion tests that wording, because a development sample is not a community norm and a reader who conflates them has been misled by this package. Second, nothing ships from a draft: the final submitted paper is the ingestion source and is machine-diffed cell-by-cell, as `pid_norms` is against markon2024. Decided by Jeff at the 2026-08-13 plan gate, over holding the line that descriptives are not norms (offered and declined) and over adopting the numbers without the development-sample labelling (offered and declined).

**Consequences:** Narrows the 2026-08-06 correction rather than overturning it — that correction's target was the unpublished development *workbooks*, which stay barred; what changes is that a published paper's table is not barred merely for describing a development sample. It does not license a T-score or percentile function for the HiTOP-SR: Table 1 carries no raw→percentile mapping, so no such table exists to ship and IP3 still bars one. It does not reach the PID-5, whose gap is reliability rather than reference statistics. D-022 is untouched — the shipped cells are the paper's own printed statistics, and the interval arithmetic is a published formula applied to them at call time, not a constant fitted from a shipped table. The evidence that would reopen this is a community-norm table for the HiTOP-SR being published, which would make a development-sample reference the weaker of two available sources.
